So the stored file and today's run can be on different stand-in constructions wherever an investor-owned stand-in meets an investor-owned candidate that has an ownership row for only part of the stand-in's window. This note counts, for each configuration the simulation's `main` runs, how far that reaches.

The host counts equal the stored file's for every entry. Every real host has a full window, so the hosts given stand-ins are the hosts as built (7, 36, 6, 5, 30).

Windows. `run_size_check` builds its windows from the usable unit-years with `log_price=0.0`; `run_new_hosts` builds them from the price rows of the listed units, kept where the unit-year is in the usable set and has a quantities row, with `log(res_price)`. `balanced` keeps a unit whose ten window years are all present and not missing. The two give the same units in the same row order if, for every usable unit-year of a listed comparison unit, the unit's outcome file holds a price row with a value above zero. The usable flag's last reason, "the constructed price is not above zero", makes this the agent's reading of what the flag guarantees, but it could only be confirmed by opening the outcome files, which this job may not do. I am uncertain about this: if an outcome file lacks a usable year or holds a nonpositive price for one, a unit present in the size check's windows would be missing from the new-host estimate's, and the counts below for the new-host estimate would be for the size check's windows. The size check's counts do not depend on this.

Possible stand-ins. `pick_stand_ins` was replicated step by step with the code's own numpy calls on the built windows, and every branch of its random choices was enumerated with its probability under the code's uniform choices: the host order (a uniform permutation, so each remaining host is next with equal probability), the substitute state (uniform over `np.unique` of the eligible states) and the stand-in (uniform over the up to five `near` rows, chosen with the code's own `np.argsort`, so its tie order is the code's). Hosts were split into groups that cannot affect one another, grown to a fixpoint: a host joins another's group when one's possible picks fall among the units the other's reachable tiers look at, or when both can reach a substitute tier and share a state. Each group was enumerated exactly. In every configuration only the tiers `own_state_and_ownership` and `own_state` are ever reached, so no substitute state is ever drawn and the substitute-state branch never arises.

Exclusions. For every possible stand-in the excluded set was computed by `Exclusions` as it stands, and by a subclass whose `__call__` is the same code line for line but calls the pre-repair module (loaded from the scratch copy as a separate module object). For a stand-in that is not investor-owned the two cannot differ, since the changed clause applies only when the stand-in, taking the host's place, is investor-owned; the computation agrees (no such stand-in differs).

Matches. In the `nearest_in_size` form, `build_blocks` takes the stand-in's region pool in its stack, removes every stand-in of the draw (by unit, across all cohorts), removes the excluded rows, and keeps the ten nearest in log size with a stable sort. In every case found the rule after the repair bars a superset of what the rule before bars, so the pool after is the pool before less the newly barred units. The ten matches therefore differ in a draw exactly when a newly barred unit in the stand-in's region, not itself a stand-in in that draw, is among the ten nearest in the pool before the repair. What was held fixed is the rest of the draw. That is not exact if it is held at one value, because other stand-ins of the same draw leave the pool and can move a candidate up. So for each stand-in with a newly barred unit in its region, each group's exact distribution was projected onto the units that can matter (the relevant stand-ins, and every possible stand-in at or ahead of the furthest newly barred unit in the stand-in's ordered pool), the projections were combined exactly across the independent groups, and the condition was evaluated, and checked against `build_blocks`' own selection, in every combination (96 combinations at 2%, 62,400 at 5%, for every cohort utility). The resulting shares are exact under the code's uniform choices.

Two things the shares are not. They are the share of draws under the uniform model of the code's choices, not a count of the draws the seeded run actually made; that count cannot be had without running the simulation, because each chunk's random stream also feeds the bootstrap and the error draws between picks. And they say only whether a stand-in's matched set differs, not how much any figure moves.

The own-state side run (`form="same_state"`). `build_blocks` uses `excluded` only in the `nearest_in_size` branch; the `same_state` branch builds its comparison cells from region and state and never calls it. The ownership rule therefore does not enter the own-state side run's construction, and it is identical across the repair in every draw, on both sets.

The second number (`run_second_number`). It builds its own `Stack` objects and calls `pick_stand_ins` on them, with no `Exclusions` and no call to `ownership.ineligible_for` or any ownership table. The repair does not enter it.

The early-years size check on made-up prices uses the same real hosts, the same windows and the same `Exclusions` as the new-host estimate on its set (exactly so under the window assumption above), so its counts are the new-host estimate's.

## Uncertainties and limits

- The shares are exact under the code's uniform choices. They are not counts of the seeded run's own draws, which cannot be obtained without running it.
- The new-host estimate's windows equal the size check's only under the reading that every usable unit-year of a listed unit has a positive price row in its outcome file (see Method). I am uncertain about this, and it could not be checked without opening the outcome files.
- Where a candidate's place sits at the edge of the ten, the result rests on exact ties being ordered as the code orders them. The replication uses the code's own sorts on the same arrays, so it orders them the same way; no other check of ties was made.
- Only the ownership repair was assessed. Other differences between the code that wrote the stored file and the code as it stands (for example the label edit to `power_simulation.py` on 2026-11-19, which the earlier assessment covers) are outside this note.
- The scripts are in the agent's scratch folder and not in the repository: `build.py` (the configurations), `count.py` (the enumeration and exclusions), `final.py` (the exact shares with the pseudo set carried through), `swaps.py` (the matched units that leave and enter).
