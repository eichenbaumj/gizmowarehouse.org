# Fingerprint dependency assessment for the ownership repair, 2026-11-19

Written 2026-11-19 by a build agent of session 21, under Joe's ruling of that day (D-107), which adopted D-106's R3 in these words: "For R3, assess all affected designs, including the 5% and rematching designs, NSTAR's support, the simulation access list, and the headline validation dependency. Expected companion changes are authorized. Stop and report unexpected changes to headline designs, access permissions, or validation compatibility. Do not rewrite stored fingerprints to make a check pass. Relabel affected old companion simulation figures; do not rerun them."

The plan, `PREANALYSIS.md`, is a DRAFT pre-analysis plan. It is not frozen and it is not registered with anyone outside. No outcome, price, revenue or bill was read for this work, and nothing under `data/blind`, `data/raw` or `data/interim/availability` was opened, listed, stated or hashed. No simulation and no step E stage was run. No stored fingerprint and no file on the list of preserved results was rewritten.

The form follows `docs/gate1/fingerprint-dependency-assessment-2026-11-19.md`. The scripts used are in the agent's scratch folder and are not in the repository: a snapshot of every design before and after the edit, built from the quantity files with the existing builders; the access list generated into scratch; the kernel's validation check run on the headline design in memory; and each summary's `main()` run with its output redirected into scratch before and after.

## Result in brief

- Every headline design is identical after the repair: the headline set at 2% and at 5%, the set with the ten-year case (2% and 5%), and the set with unsettled hosts put back (2% and 5%). Hosts, matches in order, eligible pools, support results and the design-inputs hash are unchanged. None of these designs has a partly covered investor-owned unit in the reference-year region pool of an investor-owned host, at 2% or at 5% (checked on the snapshot before the edit, then confirmed by the snapshot after it).
- The simulation's access list regenerated in scratch after the repair is byte for byte the committed one, and so is its `.sha256` file.
- The kernel accepts the validation claim for the headline design built after the repair.
- No stop condition was met. Every change is in a companion or rematching design, and every one is named below.

## (a) What changed

`pipeline/analysis/ownership.py`, sha256 `d47e5277332218fe5483718401650794891209c552e49be57591702acefd727c` at HEAD (145fd7c) and `1ffd35969e390a07dbfca41d64c8aa5269ecbe814c1b5bf10cf4bdf3e3c40039` after the edit. Four hunks:

1. The module docstring's sentence on rule 2.2 now says that an investor-owned unit with no row covering a year of an investor-owned host's window cannot be shown to be unaffiliated with that host in that year and is not eligible for that host, that rule 2.2 is read year by year (D-107), and that before the ruling the bar applied only to a unit with no row covering any window year.
2. The reason string `NO_ROW` now names the year-by-year bar. Its constant name is unchanged, so every caller that compares a reason with `ownership.NO_ROW` still matches.
3. The docstring of `ineligible_for` states the new condition.
4. The condition itself. Before, a candidate was barred when `_rows(table, c, window_years)` was empty, that is, when no row covered any window year. After, it is barred when, for some year of the window, `_rows(table, c, [y])` is empty. Nothing else in the function moved: the own-utility reason is still decided first, the same-parent reason second, `affiliates_included` still skips both of the other reasons, and the bar still applies only when the host and the candidate are both investor-owned. One edge case differs and no caller reaches it: with an empty list of window years the old condition barred an investor-owned candidate and the new one does not. Every caller passes a ten-year or thirteen-year window.

`unresolved_ownership_hosts` (the rule on hosts, including NSTAR) is untouched.

`python3 -I pipeline/analysis/pool_restrictions.py --check` printed "the ledger's transcription matches the sources" before the edit and the same line after it. `ownership.py` is not transcribed. The plan's paragraph "A row for part of a window", which is among the transcribed lines on comparison utilities, has not been changed by this agent; when the session rewrites it, the check is expected to fail by design.

## (d) The validation dependency

`outcome_analysis.read_validation_reference()` reads the `design_inputs` and `rules` components from the four step E files and from `design_support.json`'s headline set, and requires them to agree. `outcome_analysis._validation` compares the claimed design's recomputed `design_inputs` and `rules` hashes with that reference. Neither reads `code_version`, so a change to the bytes of `ownership.py` cannot by itself make the kernel refuse; only a change to the headline design could.

Checked by running the kernel's own check on the quantity files. The headline set at 2% was built after the repair with `design.build_with_rules` under the headline rules and passed to `outcome_analysis._validation(d, rules.fuel_control, None, ValidationClaim(read_validation_reference(), usable))`. Result: `passed: true`, "checked: the design's inputs and rules are those the procedure was validated on", reference read from all five files. As a control, the same claim on every cohort utility as built is refused ("the design's inputs ... differ from those of the validated design"). No estimate was made and no outcome was read.

Guards that compare a whole stored fingerprint with a live one (`inference_comparison` stage 1, stage 2 and `run_blocks`) include `code_version` and so refuse after this edit. They already refused after the label edit to `power_simulation.py` earlier on 2026-11-19 (the earlier assessment, section e). Nothing is to be run through them, and none was changed or disabled.

One guard bites on a summary: `prefreeze_summaries.main` stops when the rebuilt designs do not reproduce `design_support.json`'s matches. After the repair every cohort utility as built no longer does, so the main refuses ("stopping, nothing written") and `prefreeze_quantity_summaries.json` cannot be regenerated until `design_support.json` is. That file is on the list of results this agent may not rewrite. Whether to regenerate it is the session's decision.
